## 0. 阅读与执行约定

### 0.1 文档定位与如何使用

面向 AI Agent 的执行顺序：

1. 读 §0.2 事实基线，确认技术栈、菜单 id 段、tenant_id、Redis 缓存等硬约束。
2. 按 §1 / §2 建 4 张图谱表 DDL 与可视化只读接口（可视化零新表）。
3. 照 §0.3 四层模板写 DO / Mapper / Service / Controller，权限码统一 `hospital:模块:操作`。
4. 在 `sql/mysql/hospital_menu.sql` 追加菜单（知识图谱 7000+、可视化 7100+），并 `redis-cli flushall` 或重启后端生效。
5. 前端页放 `views/hospital/<模块>/index.vue`，API 封装用 `request`，菜单由后端驱动。
6. 按 §1.5 / §2.5 的用例用 JUnit 5 + Mockito 写 Service 层单测，再联调。

### 0.2 现有系统事实基线

- **技术栈**：Spring Boot + Vue 3 + MyBatis-Plus，基于 yudao / RuoYi-vue-pro 框架。业务模块在 `ruoyi-vue-pro/yudao-module-hospital/`，前端在 `yudao-ui-admin-vue3/`。
- **数据库引擎**：当前以 MySQL 8.0 运行，但业务代码方言无关，可平滑切到 OpenGauss（国产数据库，兼容 PostgreSQL 协议）。
  - 方言无关：业务基于 MyBatis-Plus，生成的 SQL 方言无关（实测 `StatsServiceImpl` 用 `LambdaQueryWrapperX` + Java Stream，零 MySQL 专有函数）。
  - 当前运行态：仓库 `application-local.yaml` 的 datasource 指向 `jdbc:mysql://...`，`sql/` 下只有 `mysql/` 版 DDL（含 `AUTO_INCREMENT` / `ENGINE=InnoDB` / 反引号），没有 `postgresql` / `opengauss` 目录。
  - 切 OpenGauss：OpenGauss 兼容 PostgreSQL，是设计目标。切回只需另写一份 PG 版建表脚本、测试数据按 PG 写、datasource 改回 PG，**Java 业务代码一行都不用动**。
- **业务表**：现有 10 张业务表（科室 / 医生 / 患者 / 病房 / 床位 / 就诊 / 处方 / 处方明细 / 药品 / 账单），知识图谱另加 4 张新表，可视化零新表。
- **双层（+ 数据级）权限**：① 后端操作级 `@PreAuthorize("@ss.hasPermission('hospital:X:op')")`；② 前端按钮级 `v-hasPermi` / `checkPermi`；③ 数据级 `HospitalSecurityContext` 按 doctor / patient 身份过滤。
- **菜单后端驱动**：菜单来自 `system_menu`，前端登录后按 `component` 动态加载。`src/router/modules/hospital.ts` 手写路由是死代码，把 Vue 页放 `views/hospital/<模块>/index.vue` 并在 `system_menu` 插 `type=2` 记录即可。
- **菜单 id 区间**：现有医院菜单 id 已用到 **5191**（区间 5100–5191）。知识图谱用 **7000–7099**，可视化用 **7100–7199**。
- **tenant_id**：DO 只要 `extends BaseDO` 就免费获得多租户过滤；导入 / 种子数据必须 `UPDATE ... SET tenant_id=1`，否则后端按租户过滤查不到。
- **Redis 权限缓存**：改完 `system_menu` / `system_role_menu` 必须 `redis-cli flushall` 或重启后端，否则新菜单 / 权限不生效（缓存键 `user_role_ids` / `menu_role_ids` / `permission_menu_ids`）。
- **AI 客户端现状**：无现成 DeepSeek 客户端；有框架已定义的 `RestTemplate` Bean 可用；`yudao-module-ai` 已归档退出构建，别复活。API Key 在 `application.yaml` 的 `spring.ai.deepseek.api-key`，文档与代码都不要硬编码明文。

### 0.3 通用开发规范

新增任意模块都照此清单：

- **四层模板**（都在 `ruoyi-vue-pro/yudao-module-hospital/src/main/java/cn/iocoder/yudao/module/hospital/` 下）：
  - DO：`extends BaseDO` + `@TableName("hospital_xxx")`，字段照 `MedicineDO` 改。
  - Mapper：`extends BaseMapperX<DO>`（不是原生 `BaseMapper`），分页用 `selectPage(PageParam, LambdaQueryWrapperX)`。
  - Service / ServiceImpl：`@Service`，CRUD 委托 Mapper，隐私接口调 `securityContext.requireAdmin()`。
  - Controller：`@RestController` + `@RequestMapping("/hospital/xxx")` + `@Validated`，每个方法加 `@PreAuthorize("@ss.hasPermission('hospital:xxx:query')")`，返回 `CommonResult<>`；路径 `POST /create`、`PUT /update`、`DELETE /delete`、`GET /get`、`GET /page`。
  - 权限码统一 `hospital:模块:操作`，操作取 `query / create / update / delete`。
- **建表 DDL**：每张表带逻辑删除 `deleted`、租户 `tenant_id`、审计字段（`creator` / `create_time` / `updater` / `update_time`，由 `BaseDO` 提供）；按查询维度加索引（如 `visit(dept_id, visit_date)`、`prescription_item(prescription_id)`）。
- **种子 / 演示数据**：`tenant_id=1`，外键值必须是真实存在的 id（如 `disease.dept_id` 指向 `hospital_department.id`），关联强度 / 用药类型存数字编码（1/2/3）而非中文串。
- **前端**：页放 `views/hospital/<模块>/index.vue`，API 封装用 `request({url, method})`，`url` 与后端 `@RequestMapping` 一一对应；CRUD 页照抄 `medicine/index.vue`（`el-table` + `el-dialog` + `el-pagination`）；按钮级权限 `v-hasPermi="['hospital:模块:操作']"`。
- **菜单后端驱动**：往 `system_menu` 插 `type=1/2/3` 记录（`component='hospital/<模块>/index'`），不要在前端 `src/router/modules/` 手写路由。
- **改菜单 / 权限后必须 `redis-cli flushall` 或重启后端**，否则不生效。

### 0.4 测试策略总则

- **框架**：项目用 JUnit 5 + Mockito。医院模块已有的 `*Test` 类（如 `service/medicine/MedicineServiceImplTest.java`）是标准范本：用 `@Mock` 标注 Mapper / 外部客户端，构造被测 `ServiceImpl` 后由 `MockitoAnnotations.openMocks(this)` 与 `ReflectionTestUtils.setField(...)` 注入依赖，不启动 Spring 容器、不连 DB。框架另提供基类 `ruoyi-vue-pro/yudao-framework/yudao-spring-boot-starter-test/.../test/core/ut/BaseMockitoUnitTest`（Mockito 装配）、`BaseDbUnitTest`（带库单测）等，按需继承。
- **重心**：Service 层单测为主。用 Mockito Mock 掉 Mapper（断言 `deleteById` 是否被按预期调用）与外部 `DeepSeekClient`（避免真实网络）；可视化只读聚合用 Mockito Mock 现有 Mapper 后断言 Stream 聚合结果；DeepSeek 降级 / JSON 解析重试也用 Mock 客户端覆盖。
- **交付硬门槛**：各模块具体用例见 §1.5（知识图谱）/ §2.5（可视化），必须按清单补 `*Test` 类并 `mvn test` 全绿；**单测未通过，代码不得算完成、不得进入联调**。目标接口通过率 100%。

## 1. 模块一：AI 增强医疗知识图谱

### 1.1 目标与范围

构建「疾病—症状—药品」三元组（知识图谱基本单元：主体-关系-客体）知识图谱（4 张表）并提供 DeepSeek RAG（检索增强生成）智能推理（辅助诊断、处方审核）。图谱用关系数据库的 JOIN 实现图遍历，不引入 Neo4j（图数据库）；AI 仅由服务端代理调用，前端对 RAG 链路透明。复用框架现成的 `RestTemplate` 调 DeepSeek，无新依赖。

### 1.2 数据模型

#### 4 张表字段

**hospital_disease（疾病字典）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 疾病 ID |
| name | VARCHAR(100) | 疾病名称 |
| icd_code | VARCHAR(20) | ICD-10 编码（如 J06.9） |
| category | VARCHAR(50) | 分类（内科/外科/儿科/妇产科） |
| dept_id | BIGINT | 所属科室 ID，关联 hospital_department.id |
| description | TEXT | 疾病简介 |
| typical_symptoms | TEXT | 典型症状文本（冗余存储，便于全文检索与 AI 提取） |
| is_common | SMALLINT | 是否常见病 1=是 / 0=否 |

**hospital_symptom（症状字典）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 症状 ID |
| name | VARCHAR(100) | 症状名称（如"发热"） |
| location | VARCHAR(50) | 部位（全身/头部/胸腹部/四肢） |
| type | VARCHAR(50) | 症状类型（主观感受/客观体征） |
| description | VARCHAR(500) | 症状描述 |

**hospital_disease_symptom（疾病-症状关联，图谱边）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 关联 ID |
| disease_id | BIGINT FK | 疾病 ID |
| symptom_id | BIGINT FK | 症状 ID |
| strength | TINYINT | 关联强度编码 1=主要 / 2=次要 / 3=偶见 |
| reference | VARCHAR(500) | 文献/指南依据 |

**hospital_disease_medicine（疾病-药品关联，图谱边）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 关联 ID |
| disease_id | BIGINT FK | 疾病 ID |
| medicine_id | BIGINT FK | 药品 ID，关联 hospital_medicine.id |
| usage_type | TINYINT | 用药类型编码 1=首选 / 2=备选 / 3=辅助 |

**字段约束**：`strength`、`usage_type` 只存数字编码 1/2/3（建议 `TINYINT`），前端用字典映射显示中文。不要在表里存"主要/次要/首选"等中文串，否则 `ORDER BY strength` 排序与 `WHERE strength=1` 过滤会错乱。

#### 关系说明

- 疾病节点 `hospital_disease` ↔ 症状节点 `hospital_symptom`，由 `hospital_disease_symptom` 连边，边属性 `strength`。
- 疾病节点 `hospital_disease` ↔ 药品节点 `hospital_medicine`，由 `hospital_disease_medicine` 连边，边属性 `usage_type`。
- 症状和药品不直接相连；疾病是两类边的共同枢纽。

#### 建表 DDL 关键约束

4 张表 DO 照搬 §0.3 的通用规范（`MedicineDO` 模板）：`extends BaseDO` + `@TableName("hospital_xxx")` + `@KeySequence("hospital_xxx_seq")` + `@TableId`。`BaseDO` 已自带逻辑删除 `deleted`、审计字段（`creator`/`create_time`/`updater`/`update_time`）；`tenant_id` 由多租户拦截器在 SQL 层自动注入，DO 不写该字段。DDL 建 `AUTO_INCREMENT` 主键 + `tenant_id BIGINT DEFAULT 0`。

```java
@TableName("hospital_disease")
@KeySequence("hospital_disease_seq")
@Data
@EqualsAndHashCode(callSuper = true)
@ToString(callSuper = true)
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class DiseaseDO extends BaseDO {
    @TableId
    private Long id;
    private String name;
    private String icdCode;
    private String category;
    private Long deptId;
    private String description;
    private String typicalSymptoms;
    private Integer isCommon;
}
```

#### 种子数据约定

- 所有种子/演示数据 `tenant_id = 1`（见 §0.3）。
- 量级：30 疾病 + 40 症状 + 100 条关联（disease_symptom 与 disease_medicine 合计）。
- 关联强度与用药类型一律用数字编码 1/2/3，不用中文。

#### 1.3.3 算法

**图谱查询（MySQL 语法，可移植）**

`findDiseasesBySymptoms(List<Long> symptomIds)`：按症状覆盖率降序。

```sql
SELECT d.id, d.name, d.dept_id, COUNT(ds.symptom_id) AS match_count
FROM hospital_disease d
JOIN hospital_disease_symptom ds ON d.id = ds.disease_id
WHERE ds.symptom_id IN (:ids)
GROUP BY d.id, d.name, d.dept_id
ORDER BY match_count DESC;
```

`getDiseaseNetwork(Long diseaseId)`：返回 nodes/links（疾病节点 category=0，症状=1，药品=2）。

```sql
SELECT 'symptom' AS type, s.id, s.name, ds.strength
FROM hospital_disease_symptom ds JOIN hospital_symptom s ON ds.symptom_id = s.id
WHERE ds.disease_id = :id
UNION ALL
SELECT 'medicine' AS type, m.id, m.name, dm.usage_type
FROM hospital_disease_medicine dm JOIN hospital_medicine m ON dm.medicine_id = m.id
WHERE dm.disease_id = :id;
```

`matchSymptoms(List<String> names)`：用 `SymptomMapper` 的 `LambdaQueryWrapperX.like(...)` 对 `name` 模糊匹配，返回 `List<Long>`。

`getDiseaseMedicineMapping(String diagnosis)`：按诊断文本关联疾病（用 `typical_symptoms`/`name` 模糊或精确匹配到 disease），再 JOIN `hospital_disease_medicine` 取标准用药方案，返回疾病→药品列表映射。

**RAG 流程**

辅助诊断 `assistDiagnosis(String symptomDescription)` 共 6 步：

1. `deepSeekClient.chat(EXTRACT_PROMPT, symptomDescription)` 提取症状实体列表。
2. `knowledgeGraphService.matchSymptoms(extracted)` 调 `SymptomMapper` 模糊匹配得 `symptomIds`。
3. `knowledgeGraphService.findDiseasesBySymptoms(symptomIds)` 调 `DiseaseSymptomMapper`+`DiseaseMapper` JOIN 得候选疾病（按覆盖率降序）。
4. `buildDiagnosisPrompt(...)` 拼 RAG Prompt（原始描述 + KG 匹配结果 + JSON Schema 指令）。
5. `deepSeekClient.chat(DIAGNOSIS_PROMPT, ragPrompt)` 推理。
6. 解析 JSON → `AssistDiagnosisVO`（含 `offline=false`）。

处方审核 `aiPrescriptionReview(Long prescriptionId)` 共 5 步：

1. 经 `PrescriptionItemMapper` + `MedicineMapper`（或 `MedicineService`）取处方药品；经 `PrescriptionMapper`→`VisitMapper` 取 `VisitDO.diagnosis`（已核实该字段存在）作为患者诊断。
2. `knowledgeGraphService.getDiseaseMedicineMapping(diagnosis)` 取标准用药方案。
3. `buildReviewPrompt(medicines, diagnosis, map)` 拼 RAG Prompt。
4. `deepSeekClient.chat(REVIEW_PROMPT, reviewPrompt)` 审核。
5. 解析 JSON → `ReviewResponseVO`（含 `riskLevel`/`interactions`/`offline`）。

**DeepSeek 接入**

用框架已定义的 `RestTemplate` Bean（`@Resource` 注入，见 §0.2），读 `application.yaml` 的 `spring.ai.deepseek.api-key`，**不硬编码密钥**。请求 `https://api.deepseek.com/v1/chat/completions`（OpenAI 兼容，`Authorization: Bearer <api-key>`），请求体带 `"response_format":{"type":"json_object"}` 并用 system prompt 约束 JSON Schema。

健壮性：为 DeepSeek 单独建带超时的 `RequestFactory`（`connectTimeout=5000`/`readTimeout=5000`），不动全局 `RestTemplate`；调用抛异常或超时则降级返回纯 KG 匹配结果并在 VO 标 `offline=true`；JSON 解析失败最多重试 3 次，仍失败则降级。不要复活已归档的 `yudao-module-ai`。

#### 2.3.3 聚合实现（逐图表，方言无关）

统一原则：优先用 `LambdaQueryWrapperX` 把数据 `selectList` 拉内存，再 Java Stream 聚合，零原生 SQL、自动带 `tenant_id`（注入规则见 §0.3）。只有必须下推才用 `@Select`，且写可移植 SQL，不要使用 `HOUR()`/`DATE_SUB()`/`DATE_FORMAT()` 等 MySQL 专有函数；时段、月份、年龄桶一律在 Java 侧算。多表 JOIN 若导致租户拦截器解析失败，Mapper 方法加 `@InterceptorIgnore(tenantLine = "true")` 后自行按 `TenantContextHolder.getTenantId()` 过滤，不要在 SQL 里手写 `tenant_id`。

**热力图（科室 × 时段）**
- 真实字段：`visit.visitDate`（LocalDateTime）、`visit.deptId`；`department.id → deptName`。
- 算法：先 `departmentMapper.selectList(...)` 得 `Map<Long,String> deptNameMap`；再 `visitMapper.selectList(new LambdaQueryWrapperX<>())` 全量；
  ```java
  Map<Long, Map<Integer, Long>> byDeptHour = visits.stream()
      .filter(v -> v.getVisitDate() != null && v.getDeptId() != null)
      .collect(Collectors.groupingBy(VisitDO::getDeptId,
          Collectors.groupingBy(v -> v.getVisitDate().getHour(), Collectors.counting())));
  // 展开为 HeatmapVO(deptName, hour, count)
  ```
- 坑：`visitDate.getHour()` 返回 0–23；前端把非门诊时段（如 0–7、20–23）归并或隐藏。科室名不在 visit 表，必须靠 deptNameMap 映射，不要 JOIN 下推。

**科室雷达图（接诊量 / 治愈率 / 平均费用）**
- 真实字段：`visit.status`（Integer）、`bill.totalAmount`、`bill.visitId`、`visit.deptId`。
- 算法：拉 visits、bills 全量，按 `deptId` 分组；
  - 接诊量 = 组内条数；
  - 治愈率 = 组内 `status == VisitStatusEnum.COMPLETED.getStatus()`（即 2）的计数 / 总数；
  - 平均费用 = 组内 `visitId → bill.totalAmount` 映射后求平均（`BigDecimal`，`setScale(2)` 再转 double）；
  封装 `DeptRadarVO(deptName, visitCount, cureRate, avgFee)`。
- 坑：治愈率用 `status = 2`，不要写字符串 `'已完成'`；`bill` 可能为空（`visitId` 无对应账单），求平均时跳过 null。

**患者画像（三块分开）**
- 年龄金字塔：真实字段 `patient.birthDate`（LocalDate）、`gender`。
  ```java

  // 落桶 0-17 / 18-35 / 36-50 / 51-65 / 65+，按 gender 正负向画条形
  ```
  封装 `PatientAgeVO(gender, ageGroup, count)`。
- 地区 TOP10：患者表只有自由文本 `address`，无省/市字段。方案 A 按 `address` 前缀近似（Java 侧取前 2 字符当 region）；精确需新增 `region` 字段（方案 B，见 §2.6）。封装 `PatientRegionVO(region, count)`。
- 医保占比：只有 `insuranceNo`（医保卡号），无医保类型字段。按有无医保二元：`hasInsurance = insuranceNo != null && !insuranceNo.isEmpty()`。封装 `PatientInsuranceVO(hasInsurance, count)`。

**疾病季节性趋势 ⚠️**
- 真实情况：`hospital_visit` 无结构化的 disease_id，只有自由文本 `diagnosis`。给出三套方案：
  - a) 本期先做纯就诊量按月趋势（保底）：Java 侧 `visitDate.toLocalDate().getMonthValue()` 分桶，零字段风险；
  - b) 有余力按 `diagnosis` 文本取 TOP N 粗分多 series（诊断写法不一会分散计数）；
  - c) 精确按病种等模块一知识图谱建好、给 visit 关联 `disease_id` 后再做。
- 封装 `DiseaseSeasonalVO(month, diagnosis, count)`，`diagnosis` 在方案 a 下填 "ALL" 或空串。本期默认方案 a。

**药品联合使用**
- 真实字段：`hospital_prescription_item` 的 `prescriptionId`/`medicineId`/`id`，表与字段已核实存在。
- 算法：建议 Java 侧按 `prescriptionId` 分组，组内两两组合（`a.id < b.id` 去重、避免 A-A 与 A-B/B-A 重复），统计共现次数，`>= 2` 视为高频；再 JOIN `hospital_medicine` 取药名。封装 `MedicineCooccurrenceVO(medicineA, medicineB, coCount)`。
- 若下推 SQL：`a.id < b.id` 去重 + `HAVING COUNT(*) >= 2`，药名 `LEFT JOIN hospital_medicine` 取；多表 JOIN 失败按 §0.3 加 `@InterceptorIgnore`。
