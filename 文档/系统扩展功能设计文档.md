# 第一部分：技术设计

## 一、扩展总览

### 1.1 现有基础

当前系统已实现 11 张业务表、37 个 API、14 个前端页面，覆盖门诊挂号、就诊诊断、处方发药、住院登记、账单支付等核心流程。系统采用 Spring Boot + Vue 3 + OpenGauss 技术栈，前后端分离架构。

### 1.2 为什么选这两个方向？

常规的医院管理系统扩展通常是"横向"的——加一个预约模块（3 张表 + 4 个页面）、加一个检查模块（3 张表 + 4 个页面）……这样做的好处是功能齐全，但缺点是**每个模块都是相似的增删改查**，技术深度有限，答辩时很难讲出亮点。

我们选择了"纵向"创新路线：

- **AI 增强医疗知识图谱**：不满足于"数据存在表里"，而是把数据之间的关系以图结构组织起来，再接入大模型 API（DeepSeek），让系统从"存数据"升级到"理解数据"
- **智能数据可视化**：不满足于简单的柱状图/饼图，而是用热力图、雷达图、桑基图等高级图表，让数据自己"讲故事"

**核心理念**：用 4 张新表 + 0 张新表（可视化完全基于现有数据），实现远超传统 CRUD 扩展的技术深度。

### 1.3 本次扩展范围

| 模块 | 核心能力 | 新增表数 | 新增 API | 新增页面 |
|------|---------|---------|----------|---------|
| AI 增强医疗知识图谱 | 图结构医学知识库 + DeepSeek RAG 智能推理 | 4 | 17 | 6 |
| 智能数据可视化 | SQL 聚合 → ECharts 高级图表，零新表 | 0 | 5 | 5 |

### 1.4 技术路线对比

```
         传统路线（横向 CRUD 扩展）              本系统路线（纵向创新）
         ────────────────────────              ──────────────────
   预约系统（3表 + 4页 + 6API）           AI 知识图谱（4表 + 6页 + 17API）
   检查系统（3表 + 4页 + 6API）                    ↓
   药库系统（3表 + 4页 + 6API）           关系型数据库 → 图结构建模
   护理系统（3表 + 4页 + 6API）                    ↓
         ↓                              RAG 检索 + DeepSeek 推理
   大量重复 CRUD 代码                             ↓
         12表 + 16页 + 24API            智能可视化（0表 + 5页 + 5API）
                                                  ↓
                                         实现成本低，技术深度高
```

> **通俗理解**：左边是"做加法"——每加一个功能就加一堆表和页面，工作量大但技术含量不高；右边是"做乘法"——在现有数据基础上叠加 AI 和可视化能力，用较少的新增表实现更高的技术深度。

## 二、模块一：AI 增强医疗知识图谱

### 2.1 通俗理解：什么是知识图谱？

在传统数据库里，疾病、症状、药品各自存在不同的表中，它们之间的关系通过外键关联。比如要知道"感冒有什么症状"，需要 JOIN 三张表才能查到。

**知识图谱**（Knowledge Graph）就是把这种关系用"图"的方式组织起来——疾病、症状、药品是图的**节点**，它们之间的关联（"有症状""用药品"）是图的**边**。这样做的好处是：

1. **直观**：看一张图就知道"这个疾病关联了哪些症状、该用什么药"
2. **可推理**：输入多个症状 → 沿着图的边找到关联的疾病 → 按匹配的症状数量排序，就得到了候选诊断
3. **零外部依赖**：完全用关系型数据库（OpenGauss）的 JOIN 查询实现图遍历，不需要安装 Neo4j 等专门的图数据库

### 2.2 功能描述

构建以「疾病 — 症状 — 药品」三元组为核心的医学知识图谱，结合 **DeepSeek API**（一个国产大语言模型，API 价格低廉，兼容 OpenAI 接口格式，适合课程演示）实现智能推理。

三大应用场景：

| 场景 | 输入 | 处理 | 输出 |
|------|------|------|------|
| 知识图谱可视化 | 疾病/症状 ID | SQL JOIN 查关联 | ECharts 力导向图 JSON |
| AI 辅助诊断 | 自然语言症状描述 | DeepSeek 提取实体 → KG 检索 → DeepSeek 推理 | 参考科室 + 紧急程度 + 注意事项 |
| AI 处方审核 | 处方药品列表 + 患者诊断 | KG 检索疾病-药品关联 → DeepSeek 审核 | 风险等级 + 相互作用报告 |

> **RAG**（Retrieval-Augmented Generation，检索增强生成）是本模块的核心技术架构。通俗理解就是：AI 在回答之前，先从知识图谱里"查资料"（Retrieval），然后把查到的结构化知识连同用户的问题一起发给大模型，让大模型基于真实数据来生成答案（Generation）。这样做比直接问大模型更准确，因为大模型的回答有知识图谱的数据做支撑，而不是"凭记忆瞎猜"。

### 2.3 数据库设计

#### 2.3.1 新增表清单（4 张）

所有新表遵循与现有 11 张表相同的设计规范：逻辑删除（`deleted`）、多租户（`tenant_id`）、审计字段（`creator`/`create_time`/`updater`/`update_time`）。

**hospital_disease（疾病字典）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 疾病 ID |
| name | VARCHAR(100) | 疾病名称 |
| icd_code | VARCHAR(20) | ICD-10 编码（国际疾病分类代码，如 J06.9 = 上呼吸道感染） |
| category | VARCHAR(50) | 分类（内科/外科/儿科/妇产科等） |
| dept_id | BIGINT | 所属科室 ID，关联 `hospital_department.id` |
| description | TEXT | 疾病简介 |
| typical_symptoms | TEXT | 典型症状文本（冗余存储，方便全文检索和 AI 提取） |
| is_common | SMALLINT | 是否常见病：1=是 / 0=否 |

**hospital_symptom（症状字典）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 症状 ID |
| name | VARCHAR(100) | 症状名称（如"发热"） |
| location | VARCHAR(50) | 部位（全身/头部/胸腹部/四肢等） |
| type | VARCHAR(50) | 症状类型（主观感受/客观体征） |
| description | VARCHAR(500) | 症状描述 |

**hospital_disease_symptom（疾病-症状关联）**

> 这是知识图谱中的"边"——连接疾病节点和症状节点，标注关联强度。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 关联 ID |
| disease_id | BIGINT FK | 疾病 ID |
| symptom_id | BIGINT FK | 症状 ID |
| strength | VARCHAR(20) | 关联强度：1=主要症状 / 2=次要症状 / 3=偶见症状 |
| reference | VARCHAR(500) | 文献/指南依据 |

**hospital_disease_medicine（疾病-药品关联）**

> 连接疾病节点和药品节点，标注用药类型，是 AI 处方审核的数据基础。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 关联 ID |
| disease_id | BIGINT FK | 疾病 ID |
| medicine_id | BIGINT FK | 药品 ID |
| usage_type | VARCHAR(20) | 1=首选 / 2=备选 / 3=辅助 |

> **设计说明**：为什么用两张关联表而不是一张？因为症状和药品是两类不同的事物——症状是疾病的表现，药品是疾病的治疗手段。分开存储不仅语义清晰，也方便各自独立查询和扩展。

#### 2.3.2 关键 SQL 示例

```sql
-- 图遍历：根据症状 ID 查询关联疾病，按覆盖率排序
-- 通俗理解：输入患者表现出的几个症状，找出哪些疾病包含了这些症状，
--          包含的症状越多，这个疾病的可能性越大
SELECT d.id, d.name, d.dept_id, COUNT(ds.symptom_id) AS match_count
FROM hospital_disease d
JOIN hospital_disease_symptom ds ON d.id = ds.disease_id
WHERE ds.symptom_id IN (1, 3, 7)          -- 患者症状 ID 列表
GROUP BY d.id, d.name, d.dept_id
ORDER BY match_count DESC;

-- 查询疾病的完整关联图谱（症状 + 药品）
-- 通俗理解：查出一个疾病关联的所有症状和药品，前端用 ECharts 渲染成图
SELECT 'symptom' AS type, s.name AS label, ds.strength
FROM hospital_disease_symptom ds
JOIN hospital_symptom s ON ds.symptom_id = s.id
WHERE ds.disease_id = ?
UNION ALL
SELECT 'medicine' AS type, m.name AS label, dm.usage_type
FROM hospital_disease_medicine dm
JOIN hospital_medicine m ON dm.medicine_id = m.id
WHERE dm.disease_id = ?;
```

#### 2.4.2 AiService 核心流程设计

> 以下代码为设计蓝图，展示 AI 辅助诊断和处方审核的完整处理流程。实际实现时可能根据 DeepSeek API 的响应格式做调整。

```java
@Service
public class AiServiceImpl implements AiService {

    @Resource
    private KnowledgeGraphService kgService;
    @Resource
    private MedicineService medicineService;

    /**
     * AI 辅助诊断（计划实现）
     *
     * 完整流程（RAG 架构）：
     * ① DeepSeek 提取症状实体 → ② 知识图谱检索匹配疾病（Retrieval）
     * → ③ 构造 Prompt 模板 → ④ DeepSeek 推理生成诊断建议（Generation）
     *
     * Prompt（提示词）是什么：给 AI 的指令文本，告诉它"你是谁、要做什么、
     * 输出什么格式"。好的 Prompt 是 AI 返回可用结果的关键。
     */
    public AssistDiagnosisVO assistDiagnosis(String symptomDescription) {
        // 步骤1：调用 DeepSeek 从自然语言中提取症状实体
        // 例如输入"头痛三天，伴有发热和喉咙痛"
        //    → 输出 ["头痛", "发热", "喉咙痛"]
        List<String> extractedSymptoms = callLLMExtract(symptomDescription);

        // 步骤2：在 symptom 表中模糊匹配，拿到 symptom IDs
        List<Long> symptomIds = kgService.matchSymptoms(extractedSymptoms);

        // 步骤3：JOIN disease_symptom 查询匹配的疾病，按症状覆盖率降序
        List<DiseaseMatchVO> matchedDiseases = kgService.findDiseasesBySymptoms(symptomIds);

        // 步骤4：构造 RAG Prompt（知识图谱数据 + 原始症状 + 系统指令）
        String prompt = buildDiagnosisPrompt(symptomDescription, matchedDiseases);

        // 步骤5：调用 DeepSeek 生成诊断参考建议
        String aiResponse = callLLM(prompt);

        // 步骤6：解析 DeepSeek 返回的 JSON → 返回前端
        return parseDiagnosisResponse(aiResponse);
    }

    /**
     * AI 处方审核（计划实现）
     *
     * 流程：查询处方药品 + 患者诊断 → 知识图谱检索疾病-药品关联
     * → 构造 Prompt → DeepSeek 审核 → 返回风险报告
     */
    public ReviewResponseVO aiPrescriptionReview(Long prescriptionId) {
        // 1. 查询处方药品列表 + 患者诊断
        List<MedicineVO> medicines = medicineService.getByPrescription(prescriptionId);
        String diagnosis = getVisitDiagnosis(prescriptionId);

        // 2. 从知识图谱检索疾病-药品关联（标准治疗方案是什么）
        Map<String, List<String>> diseaseDrugMap = kgService.getDiseaseMedicineMapping(diagnosis);

        // 3. 构造 RAG Prompt：知识图谱数据 + 实际处方 + 审核指令
        String prompt = buildReviewPrompt(medicines, diagnosis, diseaseDrugMap);

        // 4. 调用 DeepSeek 进行审核
        String aiResponse = callLLM(prompt);

        // 5. 解析审核结果（风险等级 + 具体建议）
        return parseReviewResponse(aiResponse);
    }
}
```

> **关于 DeepSeek API**：DeepSeek 是一个国产大语言模型，API 兼容 OpenAI 的接口格式，意味着可以用标准的 HTTP POST 请求调用，返回 JSON 格式结果。对于课程项目来说，它的价格非常低（几毛钱就能跑几十次），适合反复测试和演示。

#### 2.5.2 知识图谱可视化实现要点

> **力导向图**（Force-Directed Graph）是一种自动布局算法——节点之间有"弹簧力"（相关联的节点相互吸引），同时有"斥力"（所有节点互相排斥）。经过若干次迭代后，关联紧密的节点会聚在一起形成自然的聚类效果，非常适合展示知识图谱。

```typescript
// 调用后端获取图谱数据
const res = await getDiseaseNetwork(diseaseId)
// 返回格式: { nodes: [{id, name, category}], links: [{source, target, label}] }

// ECharts 力导向图配置
option = {
  series: [{
    type: 'graph',
    layout: 'force',        // 力导向布局：自动计算节点位置
    roam: true,             // 支持鼠标拖拽和滚轮缩放
    draggable: true,        // 节点可拖拽
    force: {
      repulsion: 300,       // 节点之间的斥力（值越大节点越分散）
      edgeLength: [100, 200] // 边的理想长度范围
    },
    data: res.nodes.map(n => ({
      name: n.name,
      category: n.category,  // 0=疾病（红色） 1=症状（蓝色） 2=药品（绿色）
    })),
    links: res.links,
    categories: [
      { name: '疾病', itemStyle: { color: '#ee6666' } },
      { name: '症状', itemStyle: { color: '#5470c6' } },
      { name: '药品', itemStyle: { color: '#3ba272' } },
    ],
    label: { show: true, fontSize: 11 },
  }]
}
```

### 2.6 初始化数据方案

从公开医学数据集批量导入，避免手动逐条录入：

- **ICD-10 中文版**：国家卫健委发布的疾病分类与代码表，可直接导出为 CSV 后批量 INSERT

## 三、模块二：智能数据可视化

### 3.1 通俗理解：可视化做什么？

现有系统的统计模块只能展示简单的数字和列表（如"今日接诊 25 人""床位使用率 66.7%"）。数据可视化模块把这些数字变成直观的图表，让数据自己"讲故事"：

- **热力图**：一眼看出哪个科室在哪个时段最忙（红色 = 高峰，绿色 = 空闲）
- **雷达图**：多维度对比科室综合能力（不是单纯比谁接诊多，而是从多个角度综合评估）
- **年龄金字塔**：看患者群体的年龄和性别分布结构

**关键设计原则**：**零新增数据库表**。所有图表数据都通过 SQL 聚合查询从现有 11 张表中实时计算，不引入任何冗余存储。

### 3.2 功能描述

| 维度 | 图表 | 数据来源 | ECharts 类型 | 能回答什么问题 |
|------|------|---------|-------------|---------------|
| 时间分析 | 科室接诊热力图 | visit (GROUP BY dept, HOUR) | heatmap | "哪个科室上午最忙？哪个时段是全院高峰？" |
| 时间分析 | 疾病季节性趋势 | visit (GROUP BY MONTH) | line | "流感在几月高发？和去年同期比如何？" |
| 能力评估 | 科室综合雷达图 | visit + bill 三维度聚合 | radar | "哪个科室接诊多但费用高？哪个治愈率高？" |
| 能力评估 | 药品联合使用矩阵 | prescription_item self-JOIN | heatmap | "哪两种药经常一起开？是否需要备货？" |
| 人群画像 | 患者年龄金字塔 | patient (GROUP BY age, gender) | bar | "来就诊的主要是哪个年龄段？男女比例如何？" |

## 六、技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| DeepSeek API 不可用 | AI 辅助诊断/审方功能无法使用 | 降级策略：使用纯知识图谱匹配结果替代，标注"离线模式" |
| DeepSeek 返回格式不稳定 | JSON 解析失败 | Prompt 中强制要求输出 JSON Schema；添加重试机制（最多 3 次） |
| 初始化数据量不足 | 图谱稀疏，症状匹配率低 | 从公开医学数据集批量导入；优先覆盖内科/儿科 30 个常见病 + 40 个症状 |
| 可视化数据不足 | 热力图/趋势图等图表内容稀疏 | 编写完整测试数据脚本，生成 100+ 就诊记录确保图表效果 |
| 四人协作代码冲突 | 开发阻塞 | 按包拆分职责（controller/service/mapper 各人独立），Controller 层用不同路径前缀 |
